# 实验 B 影响分析：预约邮件通知与开始前 2 小时提醒

> 本文件与 `deferred-work.md` 中追加的 v2 待办是本次变更的**全部写入物**。未修改任何代码，未修改 `PRD.md` / `architecture.md` / `epics.md` 正文，未新增依赖，未触碰 `architecture.md` §16 禁止技术表，未改 `sprint-status.yaml`。下文所有“建议改法”均为提案，不是已生效的文档改动。

## 0. 结论摘要

- **这不是“加一个发信函数”。** 它是三项结构性新增同时发生：账号模型第一次出现邮箱（`user` 表当前没有 email 列）、系统第一次出现出站外部集成（SMTP）、系统第一次出现后台定时行为（开始前 2 小时提醒）。
- **影响面**：PRD 有 14 处既有条目需要改、4 条新需求需要加；architecture 有 14 处章节需要改或确认、需要新增 ADR-006、需要新增 1 张表与 1 个列；epics 有 5 个既有 Story 需要改、需要新增 Epic 4（7 个 Story）和 7 处索引/映射。
- **裁决结果：方案 B（排到 v2）**，2026-11-11 已采纳；详见 §12。若客户后续不接受“上线后再做”，再按 §6.5 重新评估。只有在“上线日期可后移 ≥ 2 周 + 校园 SMTP 中继已确认可用 + 产品负责人接受修改 NFR-2”三条同时成立时，才建议走方案 A。
- **方案 A 的工作量**：开发约 6 人日，评审/联调/回归 2–3 人日，合计 8–9.5 人日；对已交付代码属于**中等偏大**破坏面——3/5 个写用例、账号 schema、启动与配置、至少 6 个既有测试文件会被改动。
- **三个硬冲突**（不解决就不能开工）：
  1. `PRD.md` §6 与 §7.2 明文写“不是通知系统 / 邮件不做”；
  2. `architecture.md` §2 明文写“没有后台任务”，§3 明文写“通知通道（邮件/短信）明确不连”；
  3. `PRD.md` NFR-2 要求“运行时不依赖外部服务”，SMTP 是中继服务，必须给出边界与降级语义。

## 2. 变更拆解：客户说的是四件事，不是三件

客户原话是“预约成功、取消预约、管理员改单三种触发，提醒在开始前 2 小时再发一次”。拆开后是 4 个通知事件、3 类触发、1 个定时任务：

| 编号 | 事件 | 触发点 | 收件人 | 发送时点 | 与事务的关系 | 失败语义 |
| --- | --- | --- | --- | --- | --- | --- |
| N1 | 预约成功 | `create_booking()` 提交后 | 预约所属学生 | 立即 | 业务事务提交后 | 不发信不回滚预约 |
| N2 | 取消预约 | `cancel_booking()` 提交后 | 预约所属学生 | 立即 | 业务事务提交后 | 同上；同时抑制未发出的 N4 |
| N3 | 管理员改单 | `edit_booking()` 提交后 | 预约所属学生（是否抄送管理员待定） | 立即 | 业务事务提交后 | 同上；旧 N4 作废、新 N4 重排 |
| N4 | 开始前 2 小时提醒 | 无 HTTP 请求触发 | 预约所属学生 | `first_slot - 2h` | 事务外定时投递 | 有界重试；超时/超次标记失败，不阻塞业务 |

**必须由人拍板的隐含决策**（不拍板就无法写出可验收的 Story）：

| 编号 | 决策 | 建议默认值 | 不决定的后果 |
| --- | --- | --- | --- |
| D1 | 邮箱必填还是选填 | 新注册必填；存量学生登录后补录；首版不做所有权验证 | 选填会让部分学生永远收不到；必填会卡住存量账号 |
| D2 | 管理员改单是否抄送管理员 | 只发学生；抄送留到下一版 | 收件人不明，AC 无法断言 |
| D3 | 距开始不足 2 小时才创建的预约 | 不发 N4（N1 确认邮件已覆盖），记录 `skip_reason=too_late` | 会出现“预约后立刻收到提醒”的怪行为 |
| D4 | 取消与 N4 的竞态（截止时间正好是 T-2h） | 以 outbox 状态为准；已 `sent` 的不可撤回，`pending` 的在同一事务标记 `superseded` | 同一预约可能既收到提醒又收到取消 |
| D5 | SMTP 通道 | 学校/实验室现有中继；需要 host/port/user/password/from/TLS | 没有通道，方案 A 无法验收 |
| D6 | 未配置 SMTP 时的启动行为 | `LAB_NOTIFY_MODE=off` 默认关闭；`smtp` 模式缺配置则启动失败 | 要么破坏“干净机器一条命令启动”，要么生产静默不发信 |
| D7 | 重试策略 | 最多 3 次，退避 30 s / 2 min / 10 min；超限 `failed` | 邮件服务器抖动会造成永久丢失或无限重试 |
| D8 | 提醒容差与过期 | 目标时点 ±5 分钟；超过 `first_slot` 仍未发出则 `expired`，不再补发 | 服务停机后可能发出“开始后才提醒”的邮件 |
| D9 | 邮件正文范围 | 设备名、本地日期与时段、slot 列表、`booking_id`；不含密码、token、SMTP 凭据 | 内容不定，无法写模板测试与脱敏断言 |
| D10 | 通知数据保留期 | outbox 成功记录保留 90 天，失败记录保留至人工处理 | 邮箱与预约快照长期堆积，违反最小化原则 |

### 3.2 新增条目（4 条需求 + 术语）

#### 提案 FR-9：预约事件邮件通知

**能力**：预约创建成功、学生取消成功、管理员改单成功后，系统向预约所属学生登记邮箱发送通知；通知失败不回滚业务写入，也不改变 HTTP 结果。

**建议的可验证后果**：

- 创建成功返回 303，`booking` 与 `occupancy` 行数正确，同时新增 1 条 `event_type=booking_created` 的 outbox 记录；SMTP 不可用时仍返回 303，业务行不变。
- 取消成功返回 303，新增 1 条 `booking_canceled`，且该预约所有 `pending` 的提醒记录在同一事务内变为 `superseded`。
- 管理员改单成功返回 303，新增 1 条 `booking_edited`，`before_json/after_json` 的 slot 集合与审计一致；旧提醒 `superseded`，新提醒按新首 slot 重排。
- 改单冲突返回 409 时，通知记录新增为 0。
- 同一业务事件重复投递不会产生两条相同 `(booking_id, event_type, generation)` 记录。
- 邮件正文、日志、审计、CSV 中均不出现 SMTP 密码、会话 token、明文密码。

#### 提案 FR-10：开始前 2 小时提醒

**能力**：每条有效预约在其首个 slot 开始前 2 小时发送一次提醒；取消后不再发送；改单后按新时段重排；服务重启后未到期的提醒仍会发送。

**建议的可验证后果**：

- 提醒的 `scheduled_at` 等于 `add_minutes_utc(first_slot, -120)`，格式为 20 字符 UTC 文本。
- 预约在 `scheduled_at` 之前被取消，提醒状态为 `superseded`，SMTP 收件数为 0。
- 改单后该预约恰好有 1 条 `pending` 提醒，指向新首 slot；旧提醒不再发送。
- 服务在 `scheduled_at` 前重启，重启后仍会补发；超过 `first_slot` 仍未发出的标记 `expired`，不补发。
- 创建时距开始不足 2 小时的预约不产生提醒，只产生 FR-9 的确认邮件。
- 提醒发送失败进入有界重试；重试耗尽为 `failed`，不改变预约状态。

#### 提案 NFR-5：通知失败隔离与可观测

业务写路径的延迟与结果不依赖 SMTP；单次 SMTP 连接与发送有超时上限；失败可重试、可查询、可人工重放；`GET /health` 不因 SMTP 不可用而返回非 200，但需能区分“通知关闭/正常/积压”。

#### 提案 NFR-6：邮箱与邮件凭据保护

邮箱只存在于 `user` 与通知表；不得进入 `audit_log`、CSV、stdout 请求日志；SMTP 密码只从环境变量读取，任何日志、异常、页面均不得回显；通知记录按保留期清理。

#### 术语表新增

§3 增加：**收件邮箱**（学生登记的邮件地址）、**通知事件**（创建/取消/改单/提醒四类）、**提醒计划**（`scheduled_at` 与状态机）、**outbox**（与业务同事务写入的待发记录）。

### 3.3 不建议顺手加的东西

以下都合理，但**不在本次三件事内**，不应借机进 PRD：管理员通知中心、短信/微信、邮件模板多语言、邮箱所有权验证、退订管理、邮件打开率统计。把它们写进 FR 会让本次变更从“范围变更”升级为“产品重做”。

## 4. Architecture 影响

### 4.1 为什么必须先有 ADR-006

按 R8，新增运行期能力之前先补 ADR。本次不是“新增一个 pip 包”（`smtplib` 是标准库），而是新增**一个出站边界、一种后台执行模型、一张持久化表与一个列**——这三件事都会让两个开发者独立实现时做出不兼容选择，正好命中 `architecture.md` §1 的 ADR 判据。

**提案 ADR-006：通知走事务性 outbox + 进程内投递，邮件不进入业务事务。**

决定：

1. 业务事务只写 outbox，不做网络 I/O。创建/取消/改单在各自 `write_tx()` 内插入通知记录，与 `audit_log` 同事务提交。
2. 事务提交后由投递器发送。投递器是单进程内的一个后台线程（由 `src/serve.py` 启动），另提供 `python -m src.notify --once` 供测试与手工补发。
3. 提醒是持久化计划，不是内存定时器。`scheduled_at` 存 20 字符 UTC 文本；重启后从库里捞未到期记录，天然支持补齐。
4. 投递语义是**至少一次**。用 `(booking_id, event_type, generation)` 唯一键防重复入队；不承诺“恰好一次”，因为 SMTP 没有事务性确认。
5. 不引入消息队列、Redis、Celery、外部邮件 SaaS。SMTP 只用标准库 `smtplib`，一次性连接、超时、关闭。
6. SMTP 配置只从环境变量读：`LAB_SMTP_HOST/PORT/USER/PASSWORD/FROM/TLS`；`LAB_NOTIFY_MODE=off|smtp`，默认 `off`，`smtp` 模式缺配置则启动失败。
7. 失败隔离：重试有上限；超限 `failed` 并保留 `last_error`；任何通知失败都不改变业务响应。

被否决的备选：

| # | 备选 | 否决理由 |
| --- | --- | --- |
| A | 在 `write_tx()` 内同步 `smtplib.send_message()` | 写锁持有时间从毫秒级变成秒级；并发用例的最坏 1.07 s 预算被击穿，409 会退化成 503，直接违反 NFR-1 的证据链 |
| B | 引入消息队列/Redis/Celery | §16 明文禁止；NFR-2 禁止外部中间件；40 人规模无收益 |
| C | 只靠操作系统 cron 调 CLI | 多一个部署件，破坏“一条命令启动”；只能作为可选兜底，不能作为唯一机制 |
| D | 下一个 HTTP 请求顺手发 | 没请求就不发；提醒必然迟到；失败不可追踪 |
| E | 第三方邮件 API/SaaS | 外部云服务 + 凭据 + 出网依赖，与 NFR-2 冲突 |
| F | SQLite 触发器发信 | 数据库内不能做网络 I/O；行为隐形、不可测 |

### 4.3 数据模型提案（只写提案，不落库）

```sql
-- 002_notifications.sql（提案，未创建）
ALTER TABLE user ADD COLUMN email TEXT;

CREATE TABLE notification_outbox (
    id              TEXT PRIMARY KEY,
    booking_id      TEXT NOT NULL,          -- 故意不加 FK：取消会删 booking，取消通知不能被级联带走
    event_type      TEXT NOT NULL CHECK (event_type IN (
                      'booking_created','booking_canceled','booking_edited','reminder')),
    generation      INTEGER NOT NULL DEFAULT 1,
    recipient       TEXT NOT NULL,          -- 入队时快照，避免发送时用户改邮箱造成错发
    payload_json    TEXT NOT NULL,          -- 设备、slot 列表、booking_id；不含密码/token
    scheduled_at    TEXT NOT NULL,          -- 20 字符 UTC 文本
    state           TEXT NOT NULL CHECK (state IN (
                      'pending','sending','sent','failed','superseded','expired')),
    attempts        INTEGER NOT NULL DEFAULT 0,
    last_error      TEXT,
    created_at      TEXT NOT NULL,
    sent_at         TEXT,
    CONSTRAINT uq_notification_event UNIQUE (booking_id, event_type, generation)
);

CREATE INDEX idx_notification_due ON notification_outbox(state, scheduled_at);
```

设计要点：

- **不能给 `booking_id` 加 `ON DELETE CASCADE`**。取消动作会删除 `booking` 行，如果 outbox 跟着级联，“取消通知”会在发出前被自己删掉。用快照 + 无 FK，或 `ON DELETE SET NULL`。
- **`recipient` 做快照**。发送时再 join `user` 会让“改邮箱后旧事件发到新地址”，也会让已删账号的通知无法追查。
- **`generation` 支持改单重排**。同一 `booking_id` 的第 n 次改单产生 n+1 代提醒；旧代 `superseded`，唯一键保证不会重复入队。
- **不改 `audit_log` 的 CHECK**。SQLite 不能 `ALTER` CHECK，扩 action 要重建表并搬运历史数据；本需求不需要把“发信成功”写进业务审计，outbox 状态足够。
- **不改 `001_init.sql`**。迁移器按 `PRAGMA user_version` 顺序应用 `002_*.sql`（`src/data/migrations.py`），新增文件即可，历史迁移保持不可变。

### 4.4 实现时必须避开的坑

| 坑 | 后果 | 规避 |
| --- | --- | --- |
| 在 `write_tx()` 内发信 | 写锁被网络占用；NFR-1 并发证据失效 | 事务内只 `INSERT outbox`，发送在提交后 |
| 后台线程复用 `get_db()` | `flask.g` 只存在于请求上下文，线程里直接抛异常 | 用 `src/data/db.py:15` 的 `connect()` 自建连接，并在退出时关闭 |
| 用 `datetime.now()` 或手拼 `-2h` | 违反 R4；时区/格式漂移 | 只用 `now_utc()` 与 `add_minutes_utc(first_slot, -120)` |
| 取消时先删 booking 再想发通知 | 收件人与 slot 快照已丢失 | 在同一事务内先写取消 outbox（带快照），再删 booking |
| 改单时只发新通知、不作废旧提醒 | 学生会收到旧时段提醒 | 同一事务把旧 `reminder` 置 `superseded`，再插入新代 |
| 提醒晚于开始仍补发 | 学生到场后才收到“2 小时后开始” | 发送前比较 `now_utc()` 与 `first_slot`；超时置 `expired` |
| 把邮箱写进审计/CSV/日志 | 违反 NFR-4 精神与 NFR-6 | `redact` 白名单不新增 email；CSV 六列不变；请求日志只记 user id |
| 测试里用 `smtpd` | Python 3.12 已移除该模块 | 手写最小 socket SMTP 替身，或 monkeypatch `mailer.send`；引入 `aiosmtpd` 必须另补 ADR |
| 失败无限重试 | 堵塞投递器、日志爆炸 | 有界重试 + `failed` 终态 + 人工重放命令 |

**风险**：客户明确要“自动发邮件”，C 方案是**换目标而非满足目标**。只有客户接受“我们要的是学生不错过，而不是必须走邮件”时才成立。

### 6.5 推荐与决策树

**推荐 B**，理由排序：

1. 这是上线前，最贵的不是开发 6 人日，而是**回归时间**。12 个已交付 Story 的正确性证据（尤其 NFR-1 的 120 轮并发）比一个通知功能更值钱。
2. 通知是“外部依赖 + 后台任务 + PII”三合一，任何一项在真实校园网里翻车，都会让“预约系统不可用”的锅落到主功能上。
3. B 不妨碍满足客户：v1.1 可以按本文件直接开工，且能用真实数据把提醒策略（D3/D4/D8）调对。

决策树：

```text
客户是否接受“上线后 2–3 周交付”？
├─ 是 → B（推荐）；上线同时给 C1 作为即时改善
└─ 否 → 上线日期能否后移 ≥ 2 周？
        ├─ 能 → 校园 SMTP 中继是否已确认可用？
        │       ├─ 是 → A（必须先做 ADR-006 + 改 NFR-2/§6/§7.2 并同步 §11）
        │       └─ 否 → B + C1；不要在没有通道的情况下开工
        └─ 不能 → C（C1/C2 组合），并让客户书面接受“不发邮件”
```
